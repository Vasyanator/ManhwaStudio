# ManhwaStudio for Android

Gradle project of the Android app (arm64-v8a, Android 12+ / API 31). The app is the Rust
library `manhwastudio_rs` (built as a `cdylib`) hosted by a `GameActivity`; this directory holds
only the thin Android shell. Build it with the script in the repository root:

```bash
./build-android.sh            # release-profile native library, APK in android/app/build/outputs/apk/debug/
./build-android.sh --install  # ... then `adb install -r` and launch on the connected device
./build-android.sh --logcat   # ... then follow the app's logcat
./build-android.sh --full     # also bundle the extended CJK fonts (fonts/ui/ext) and the wiki
./build-android.sh --debug    # Rust dev profile instead of release
```

The APK is always Gradle's debug variant, signed with AGP's debug keystore
(`~/.android/debug.keystore`); release signing is not set up yet.

## Prerequisites

- Rust with `rustup target add aarch64-linux-android` and `cargo install cargo-ndk`.
- Android SDK with `platforms;android-35` (AGP downloads its build-tools on first use when the
  SDK licenses are accepted), an NDK (r27 is used), and a JDK 17+ (21 recommended).
- Locations come from `ANDROID_HOME` (or `ANDROID_SDK_ROOT`), `ANDROID_NDK_HOME` and `JAVA_HOME`,
  or from `android/local.properties` (gitignored; never commit it):

  ```properties
  sdk.dir=/path/to/android-sdk
  ndk.dir=/path/to/android-sdk/ndk/<version>
  java.home=/path/to/jdk
  ```

  Without an NDK location the newest NDK under `$ANDROID_HOME/ndk` is used.
- A git checkout: the bundled files are taken from `git ls-files`, so local untracked fonts never
  end up in the APK. The one exception is the launcher background folder `ui_new/menu_imgs`
  (see "Bundled files and the runtime root").
- The winit / egui fork checkouts under `crates/` that the root `Cargo.toml` patches in.
- Gradle itself is fetched by the wrapper (`gradlew`, pinned version + SHA-256); network access
  is needed on the first build for Gradle, AGP and the AndroidX libraries.

## Layout

- `settings.gradle.kts`: repositories, including the local Maven repository of
  `rustls-platform-verifier` found through `cargo metadata` (the crate ships its Kotlin
  component as an AAR inside its source), and the `:winit-secondary-window` module (see
  "Secondary windows" below).
- `app/build.gradle.kts`: SDK levels, versions (versionName = root `Cargo.toml` version,
  versionCode = major * 1000000 + minor * 1000 + patch), dependencies, packaging.
- `app/src/main/AndroidManifest.xml`: `LaunchActivity` (launcher entry) and `MainActivity`
  (the `GameActivity`, `android.app.lib_name = manhwastudio_rs`).
- `app/src/main/kotlin/io/github/vasyanator/manhwastudio/`:
  - `LaunchActivity.kt`: installs the bundled files on a worker thread, then starts `MainActivity`;
  - `AssetInstaller.kt`: copies `assets/ms_root/**` into `filesDir/ms_root` (the Rust runtime root);
  - `MainActivity.kt`: the `GameActivity`; hands over to `LaunchActivity` when the files are stale
    and routes physical-keyboard keys past GameTextInput (see "Keyboard and soft keyboard");
  - `platform/SafBridge.kt` + `platform/SafRequestActivity.kt`: the Storage Access Framework
    half of the Rust file dialogs (see "File dialogs" below).
- Generated by `build-android.sh`, gitignored: `app/src/main/jniLibs/`, `app/src/main/assets/`,
  `app/src/main/res/mipmap-xxxhdpi/ic_launcher.png`.

## Secondary windows

Extra OS windows (DeX, free-form windowing) are `rs.winit.android.SecondaryWindowActivity`
instances, one task each, shown in Recents. Their Kotlin code is the Gradle library module
`android/winit-secondary-window` INSIDE the winit fork; `settings.gradle.kts` includes it from
the winit source `cargo metadata` resolves, so it follows the `[patch]` path now and a git
dependency later. The app adds `implementation(project(":winit-secondary-window"))`, the
application meta-data `rs.winit.android.NATIVE_LIB = manhwastudio_rs` and `REORDER_TASKS`. Contract
and lifecycle: `crates/winit/src/platform_impl/android/secondary/MODULE_README.md`; inclusion
details: `crates/winit/android/README.md`.

## Window insets

Android draws the app edge-to-edge (enforced from targetSdk 35): the status bar, the gesture /
navigation bar, a display cutout and the on-screen keyboard overlap the window. The winit fork
reads each window's insets through the `winit-secondary-window` module (also for the main
`GameActivity`) and egui keeps its panels inside the resulting safe area, the keyboard included
(contract: `crates/winit/src/platform_impl/android/MODULE_README.md`). Therefore the manifest
must not opt out of edge-to-edge, and `MainActivity` keeps `windowSoftInputMode="adjustResize"`,
which makes Android report the keyboard as an inset instead of panning the window.

## Keyboard and soft keyboard

GameActivity's text input (GameTextInput) is an `InputConnection` that is also the key listener
of the surface view: while the soft keyboard is requested (a text field has focus) it swallows
every printable key into its own Java buffer. `MainActivity.dispatchKeyEvent` therefore sends
key events of real keyboard devices straight to `onKeyDown` / `onKeyUp` (the native key path), so
a physical keyboard types, switches layouts and triggers shortcuts the same way whether a field
is focused or not. Soft-keyboard input still goes through GameTextInput, and the winit fork turns
its text into IME events (contract: `crates/winit/src/platform_impl/android/MODULE_README.md`);
each key therefore reaches the app exactly once.

The fork requests the soft keyboard explicitly when a text field gains focus. With a hardware
keyboard attached Android still shows at most the IME's toolbar unless the system setting
"show on-screen keyboard" (`show_ime_with_hard_keyboard`) is on; that is the platform's
behaviour, not a bug.

## File dialogs (Storage Access Framework)

The Rust file-dialog seam (`crates/ms-platform`, `file_dialog/android.rs`) loads
`io.github.vasyanator.manhwastudio.platform.SafBridge` by name (the one owner of the name is
`SAF_BRIDGE_CLASS` in `crates/ms-platform/src/android/saf.rs`; renaming or moving the class
breaks every file dialog). `SafBridge.launch` posts to the UI thread and starts the translucent
`SafRequestActivity`, which runs the AndroidX Activity Result contract of the request
(`OpenDocument`, `OpenMultipleDocuments`, `OpenDocumentTree`, `CreateDocument`) and reports
the picked URIs and names through the Rust native `SafBridge.nativeOnResult`. Picked inputs are
then copied into the app cache by Rust through the blocking `SafBridge` helpers; outputs are
written to a local staging file or folder and streamed into the chosen document or tree on
commit. The JNI contract is documented in `SafBridge.kt` and in the ms-platform
`MODULE_README.md`; the `native` method name and every static helper signature are part of it.
No storage permission is declared: SAF grants are per document, persisted only for the time
of a copy or commit and released afterwards.

## Bundled files and the runtime root

The Rust side runs with `filesDir/ms_root` as its working directory and runtime root
(`src/android_entry.rs`). The script bundles the tracked `fonts/` files (without
`fonts/ui/ext` unless `--full`; `--full` also adds `wiki/`), the launcher background images
(`ui_new/menu_imgs`, see below) and two control assets: `ms_root.files` (the file list) and
`ms_root.stamp` (a content hash of the bundle: file paths and contents).

The launcher backgrounds are third-party comic pages kept only locally: `ui_new/` is not tracked
and must never be added to git or the `.gitignore` allowlist. The script therefore stages them
from the working tree on every build (not only `--full`): the regular files directly in that
folder with an image extension the launcher reads (`is_supported_image` in
`crates/ms-launcher/src/background.rs`). When the folder is missing or empty (a fresh clone) it
prints a warning and the APK builds without them; the launcher then shows no built-in
background. AGP stores `.png` / `.jpg` / `.webp` assets uncompressed by default, so they cost
their file size in the APK (~8.7 MB). The launcher finds them because the runtime root resolves
to the working directory `ms_root` there (no program markers, `ms_config::runtime_root` rule 4).

`AssetInstaller` deletes the installed stamp first, copies every file through a temporary file
and an atomic rename, removes files that an earlier bundle installed and this one no longer
ships, and writes the stamp LAST. It only ever overwrites or deletes files it installed itself;
user documents (`user_config`, `fonts_data`, presets, imported fonts, projects) are never
touched. The native side refuses to start unless the installed stamp equals the bundled one, so
a stale or half-copied root is never used. An APK update that leaves the bundle unchanged
copies nothing; one whose bundle changed (a font or a background image added, edited, renamed
or deleted) gets a new stamp, so the installer re-copies the bundle and deletes the files that
are no longer listed.

## Device notes

- Use one `adb` binary consistently: two different adb versions kill each other's server and
  drop wireless connections. The script calls the `adb` on `PATH`.
- `adb shell run-as io.github.vasyanator.manhwastudio ls files/ms_root` inspects the runtime
  root (works because the APK is debuggable).
- Logcat tag `ManhwaStudio` carries the app's `log` lines and the winit fork's `tracing` lines
  (`winit ime:`, `winit insets:`, warnings), at Info level and above.
